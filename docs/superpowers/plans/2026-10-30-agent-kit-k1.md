## 0. Decisions

### 0.1 Fixed by the user (2026-10-30)

1. **Q3: the Claude Agent SDK is the only agent engine for Claude.** The classic homegrown loop (`llm_agent/runtime`: `loop.mjs`, `fence.mjs`, `route.mjs`, `openai-tools.mjs`; Mac `CodeAssistTransport`) is retired in stages. Non-Anthropic providers get a **small separate completion/tool adapter** (evaluate the Vercel AI SDK against keeping only the OpenAI-compatible path; **no LiteLLM**, 2026 supply-chain incidents). Plain chat for them needs no loop.
2. **Token burn is mostly our configuration.** The **first track** is a *lean SDK configuration* pass, measured on the token bench before and after (items L1 to L12, section 3.1). Bench gates: 15% token and 30% time regression thresholds per the bench how-to.
3. **Q2: ended chats continue on a fresh SDK session** seeded with a short per-chat summary (made on a cheap model at archive time) plus the last 4 to 6 turns; older detail comes back on demand through `search-kb`. **Resume, not fresh, only when the chat is warm** (last activity under the cache TTL). **Never cold-resume a long transcript** (about 156k billable for the first turn at 125k context, the user's figure).
4. **Q9: triage the 129 `needs-human` SDK surface rows** by *removes our own code > saves tokens > improves safety*; ignore about 20 rows of irrelevant tools and UI plumbing. **Adopt first these 15, as separate bench-gated tasks, never inside K1:** `options.sessionStore`; `options.agents` + `tools.AgentInput` (Haiku search subagent); `options.fallbackModel`; `messages.SDKAPIRetryMessage`; `messages.SDKRateLimitEvent`; `messages.SDKPermissionDeniedMessage`; `messages.SDKModelRefusalFallbackMessage` / `NoFallbackMessage`; `messages.SDKThinkingTokensMessage`; `tools.Task*` (replace our `task-create` / `task-update` MCP tools, check availability); `options.skills`; `options.sandbox`; `query.mcpServerStatus`; `options.resumeSessionAt` + `options.resumeDropsTurn`; `options.agent` (persona and mode without rewriting the system prompt, which would let `snapshot: true` return); `tools.EnterPlanMode` / `ExitPlanMode` (lower priority). Extend the ledger to module-level functions (`listSessions`, `getSessionMessages`, `deleteSession`, `forkSession`). Updating `sdk-surface.json` is a task; the human approval of the triage is **the user's approval of this list on 2026-10-30**.
5. **Q4: the plugin / MCP / LLM-source UI** (about 5 457 lines in `Features/Library`, 5 355 without `McpConnectorAdapter`) **and its 37 routes in `server/auth-routes.mjs` move to agent-kit ownership.** Library keeps notes and sources only.
6. **Migration order:** (1) lean-config pass; (2) SDK triage plus top-15 adoption; (3) `RegressionRunner` to a plain completion route; (4) extension `/chat` removal per the data-lifecycle decision (remove `/chat` and `/kb/chat/sessions` from `REQUIRED_ENDPOINTS`, bump `MIN_SERVER_API_VERSION`), coordinated with live-then-archive; (5) legacy chats continue on v2 via the summary-plus-recent-turns path, and **stop stamping new chats classic**; (6) non-Anthropic adapter, then delete the fence loop and `CodeAssistTransport`; (7) retire `runtime/` after one release (K4) with an API version bump for the removed routes.

### 0.1b Answered by the user (2026-10-30, after the plan was written)

- **Q-T8:** `ask` mode becomes **read-only** (no `Bash`, `Edit`, `Write`); behind a switch, bench-checked before it is the default.

### 0.2 Formerly open (now answered in 0.1b)

The SDK terms say third-party developers may not offer claude.ai login or its rate limits without Anthropic's approval. LLM-IDE has a `claude login` subscription path (ambient auth, `sdk/transcripts.mjs:32-38`, `sdk/auth.mjs:37-38`, and the CLI fallback). The user decided to keep it alongside API keys (0.1b, Q-T1). ### 0.3 Non-goals

Behaviour-changing SDK adoption inside a K1 task (the template forbids it: each ships on its own commit and bench gate); changing the 16 SSE event types or `AgentV2Event` decode (additive events only, with a version bump); moving Mac chat persistence (live-then-archive owns it); the Tauri screens (K3); LiteLLM in any form; a new loop of our own for non-Anthropic providers.

## 1. Architecture decision

### 1.1 The question

With the SDK as the only Claude engine, what stays ours, what goes, and what carries non-Anthropic providers and the remaining classic callers?

### 1.2 Decision (follows 0.1, nothing new decided here)

| Concern | After K1 | Why |
|---|---|---|
| Claude chat, Loop agent, subagents | SDK `query()` only (`sdk/engine.mjs`, `sdk/loop-agent.mjs`) | The user's Q3; the skeleton principle (delegate tool loop, caching, compaction, subagents) |
| Our control layer (owned) | Permission (`tools/gates.mjs`, `canUseTool`, hooks), budget (`maxBudgetUsd`, tier routing, ledger), tenancy (`subprocess-env.mjs`, per-user config dir), memory, wire contract | Owned per K0 section 4; unchanged |
| One-shot Claude completions (no tools): Regression replay and judge, summaries, classifier, memory extraction | A plain completion route over `providers/runtime.mjs` `runClaude` (not a loop) | Needs no loop (F11) |
| Non-Anthropic chat (OpenAI, Google, DeepSeek, custom) | Small adapter in `providers/`: plain chat needs no loop; **tool use only if the evaluation says it is worth it** (section 3.8) | User decision; the SDK speaks only the Anthropic Messages API (`AgentV2Selection.agentCapableProviders`, `AgentV2Selection.swift:45`) |
| Ended chats | Fresh SDK session from a stored summary plus last 4 to 6 turns; resume only when warm (section 3.4) | Q2 |
| Plugin / MCP / LLM-source UI and routes | agent-kit owns them (section 3.10) | Q4 |

### 1.3 Options considered for the non-Anthropic adapter (evaluation is a task, not a verdict)

| Option | For | Against and unknowns |
|---|---|---|
| **A. Keep only the OpenAI-compatible path we have** (`providers/providers.mjs` 1 432 lines: routing, OpenAI/Google adapters, CLI spawn) | No new dependency; already tested; custom providers are OpenAI-compatible by construction | Tool use would need our own tool-call translation (what `openai-tools.mjs`, 70 lines, does today); Google is its own adapter |
| **B. Vercel AI SDK** | One interface over many providers, tool-call and streaming normalised | A new third-party dependency on the server boot or request path; supply-chain exposure (the stated reason LiteLLM is ruled out) must be assessed the same way (pin exact, lockfile, review, no postinstall); version and licence **not verified** here |
| **C. No tools for non-Anthropic providers** | Smallest; "plain chat for them needs no loop" | Loses what classic gives today for these providers (agent tools in chat); a product decision |

Recommendation for the task (not a decision): start with **C + A** (plain chat through the existing adapters, no loop), time-box the evaluation of B to a one-page memo, and keep a tool path only if a measured user need appears. The decision is listed as Q-T4. **Settled (Q-T4 answered, T6.1 done 2026-10-29): option B, the Vercel AI SDK behind `providers/adapter/`, with tools; the classic loop stays only until the second half of Phase 6.**

### 3.4 Ended chats: summary plus recent turns (Q2)

**Today.** After quit, live-then-archive purges `agent_sessions`, `session_memory` and the SDK transcript (live-then-archive 3.2). A new turn on an ended chat sends `fresh: true` plus the packed history (`AgentV2Transport.swift:275-281`; `ChatEngine.historyForRequest` up to 400 000 chars, `ChatEngine+History.swift:12-18`; server reads it as `freshTurnHistory`, `routes/agent-v2.mjs:252-253`). That is the "cold replay of a long transcript" the user rejected (about 156k billable at 125k context, user's figure).

**Design.**

1. **Per-chat summary at archive time.** When a chat is archived or purged (quit, sweep, idle), a cheap-model call (tier `subagent`, same tier the judge uses) writes a short summary (target 300 to 600 words, hard cap in chars) and the Mac stores it **in the same session file** as an optional field (`ChatSession.summary`, `summaryUpTo` = last message id covered). No new store: the Mac chat file stays the one copy (live-then-archive 0.1a). Extension-archived chats get the same field.
2. **Continuation.** A turn on a chat whose server mapping is gone builds a fresh SDK session whose first user message carries: the summary, the **last 4 to 6 turns verbatim** (clipped by the existing `maxHistoryTurnChars`), and one line saying older detail is available through `search-kb` / `Read`. The wire field stays `history` (so no breaking change); the Mac packs fewer, shorter turns. Server side `freshTurnHistory` already accepts it.
3. **Older detail on demand.** The `search-kb` handler (`runtime/handlers/search-kb.mjs`) searches notes and sources; archived **chat** text is not indexed today (live-then-archive 3.8 indexes notes; "chats are not indexed today"). Either (a) add a Mac-fed chat kind to the index (redacted, rebuildable, per R3), or (b) give the agent a `read-archived-chat(id, query)` tool backed by the Mac's file. Which one is **Q-T5**; until it is chosen the continuation path says only "ask the user if older detail is needed", which is the honest fallback.
4. **Warm resume.** If `now - lastUsedAt < cacheTtl` and the server mapping still exists, resume (`resumeSdkSessionId`), never fresh. `cacheTtl` is the actual TTL in force (5 minutes default; 1 hour if L7 ships), read from one constant shared by Mac and server. If a mapping exists but the chat is cold, **do not resume** a long transcript: start fresh from summary plus recent turns (the user's "never cold-resume a long transcript"). A short transcript (under a size threshold, Q-T6) may still resume, because the cache write costs less than a summary call.
5. **Summary is derived data, never the only copy.** It is rebuilt from the file on demand; losing it costs one summary call, not content.
6. **Redaction.** The summary model sees raw text; the summary is stored raw like the file (live-then-archive Q4 default). It must not be replayed into an index without redaction (live-then-archive 3.9 applies).

**Kill switch.** `LLMIDE_V2_CONTINUE=replay|summary` (default `replay` until the bench and a manual check pass; `replay` is today's behaviour) and the Mac pref `chat.continueMode`.

**Bench.** New `ended-chat-continue` scenario: seed a 30-turn chat file, drop the server mapping, send one turn; compare billable tokens `replay` vs `summary`. Gate: `summary` must be no worse than 30% of `replay` on tokens on a long seed, and **no worse than `replay` on a 4-turn seed** (a summary call must not cost more than it saves on short chats).

## 6. Bench gates

### 6.1 Per-item gate for a default flip

All against the same-session control, Haiku 5.5 **and** the Sonnet-class baseline, `--repeat 5`, run in one sitting, interleaved A/B:

1. **No scenario** regresses more than **15% billable tokens** or **30% time** (the bench's own thresholds, with its 500 ms floor) against the control.
2. The item's **target scenarios** show the claimed gain: at least 5% median billable reduction (below that the noise in F5 makes the result unusable), or the item is recorded "no gain".
3. **Hops**: median hops per scenario must not rise more than 20% (this is the guard the compact prompt failed on read-only search, +55% tokens from 2x hops).

## 7. Rollout, N-1 and rollback

- **One release per behaviour change, flag first.** Server-side flags default off in the commit that adds them; a second commit flips the default after the gate. The Mac normally spawns its own backend (`BackendManager`), so Mac and server move together; an **adopted external server** keeps its own env and version (`LLMIDE_FEATURES` memory in CLAUDE.md), which is the skew case.
- **App N-1 against server N** (adopted external server newer than the app): additive events are ignored by old decodes (confirm); removed routes answer `410` for one release, never a bare 404; `REQUIRED_ENDPOINTS` and `MIN_SERVER_API_VERSION` move only in the release that ships the matching extension.
- **App N against server N-1** (older adopted server): the Mac must keep working against a server without `POST /kb/complete`: on a 404 the runner falls back to `/code-assist` (same pattern as `AgentV2Selection.swift:222-228`, K0). Same for the summary route (fallback: replay). Until P6 the classic path stays compiled.
- **Mac chats stamped classic (N-1 data):** `ChatSession.engine == nil` files exist on every long-time user's disk. P5 never rewrites a file before a successful v2 turn; an old build that opens a migrated file sees `engine = "agentV2"` and uses its own v2 path (its `useV2` needs the same three conditions, `AgentV2Selection.swift:84-88`), so a rollback to an older app is safe. The new `summary` field is optional; an old build drops it on re-save (live-then-archive F14), costing one summary call, not content. Keep a real old-format fixture for each: `engine == nil`, `engine == "agentV2"`, with and without `projectId`.
- **Rollback per step:** flip the kill switch (3.11), or revert the default-flip commit; the code path stays for one release. Deleted code (P6, P7) is the only non-switch rollback: it is a `git revert` of a mechanical deletion, which is why P6 and P7 are separate releases (K4 rule).
- **Data:** nothing in this plan migrates a store. The chat file gains optional fields; the server gains no table. The one irreversible thing is the removal of routes, which is why they go through `410` first.
- **Soak:** after each flip, one week of normal use with the usage ledger and the per-turn composition row watched (`/kb/storage`, the activity feed); the bench is nightly or on demand, not a push gate.

### 14.1 What can and cannot be preserved (state this in the UI too)

- **Prompt caches are per provider and usually per model, and cannot be transferred.** A switch always pays **one cold prefill** on the new side. This plan makes switching *cheap* (small handoff, no cold replay of a long transcript) and *rare* (sticky while warm); it cannot make it free.
- **Preserved across a switch:** the provider-neutral conversation (the Mac session file, the one copy, live-then-archive 0.1a), the handoff note (the P5 summary, 3.4), session memory facts (`session_memory`, keyed by the same `chatSessionId`, deleted with the chat at `routes/agent-v2.mjs:785`), and the chat's settings (mode, workspace, limit).
- **Lost on a switch:** the old side's cache and, for Claude, the SDK session (`agent_sessions.sdk_session_id`, `0029_agent_sessions.sql:3-15`). Switching away from Claude and back is a **fresh** SDK session seeded like an ended chat (3.4 step 2), never a resume of a cold transcript (3.4 step 4).
- **Prior art (user's sources, not re-read):** FreeLLMAPI keeps sticky sessions (30 min), an optional handoff note, opt-in compression (dedupe, tool-output filtering, JSON compaction, stale-context trimming) and learned per-key RPM/RPD/TPM/TPD with 429/5xx cooldown plus next-model retry. OpenRouter routes sticky per `session_id` (10 min idle) and falls back **only on a provider error**. We adopt the policy shapes, not their code.

### 14.2 Where the record lives (decision, with reasoning)

**Main DB, new table `chat_session_route` (migration `0053`)**; the history of switches goes to **`agent.db`** (`agent.db` migration `0004`).

- The route row **enforces a limit**, so it must fail closed and be read in the same place as the budget. `agent-store` decision 1 keeps live state in the main DB (`agent-store.md:8-13`: `agent_sessions`, `session_memory`, `model_limits`, `quota_state`), `agent.db` is "history, never enforcement" (`kb/agent-db.mjs:1-13`: opens lazily, may be `down`, queue drops rows over `QUEUE_MAX`; `kb/agent-migrations/0001_agent_store.sql:16-18`: budget reads never use it; `0002`: `usage_calls` is a shadow, not authoritative), and the session mapping the router must stay consistent with is `agent_sessions` in the main DB. One better-sqlite3 transaction across `agent_sessions` and the route row is possible only in one file.
- The per-turn row is cheap and synchronous. The **history** (switch events) is metadata, best effort, shown in agent history: `agent.db`, written through the existing queue (`WRITE_KINDS`, `agent-db.mjs:31`), listed in `AGENT_USER_TABLES` (`agent-store.mjs:34-37`) so `purgeUser` and the enumerator test cover it. Losing history rows must never change routing.
- **Fail closed rule:** when a limit is set (or the router flag is on) and the route row cannot be read or updated, the turn is refused with 503 `ROUTE_UNAVAILABLE` before any model call. With the flag off nothing here runs and no turn is affected.

### 14.3 Routing policy

1. **Sticky while warm.** A turn goes to the row's provider/model while `now < sticky_until`. `sticky_until = last cache touch + TTL(provider)`; each completed turn refreshes it. After expiry the router may re-pick with no cache cost to lose (a warm-expired switch is free of cache loss, still pays the handoff).
2. **TTL table (a constant map in one module, shared with 3.4's `cacheTtl`):** Anthropic API key 5 min default, 1 h with the L7 extended TTL or the subscription (**the user's figures; the plan's L7 and 3.4 say 5 min default / 1 h if L7 ships; not re-verified here**); OpenRouter sticky routing 10 min idle (user's source, unverified here); OpenAI, Gemini, DeepSeek, Groq, xAI, Mistral, Together, Cerebras, Ollama: **unverified**, default to **10 min with the entry marked `ttlSource: 'assumed'`** in `server/provider-catalog.json` until each doc is read (Ollama: local KV cache, no TTL concept, treat as no stickiness needed). An unverified TTL only affects when the router *may* switch, never correctness.
3. **Switch only on:** user change; rate limit (429, existing `noteProviderRateLimited` cooldown, `provider-fallback.mjs:48-52`); provider error (5xx, auth, unavailable); session cap (14.3 item 5, which is a **stop**, not a switch, unless the user set a cheaper fallback model for the chat); or warm expiry **with** a user-ordered fallback list, and then only when the new pick is cheaper per the catalog (an explicit user opt-in, off by default). Never because another provider "looks" better.
4. **Never mid-stream.** The pick happens once at turn start, the same rule as `pickTurnProvider` (`provider-fallback.mjs:9-14,82`). A 429 mid-turn ends that turn with a retryable error; the next turn re-picks. A PUT during a running turn (`isChatTurnInFlight`, `routes/agent-v2.mjs:183`) is stored as *pending* and applied at the next turn start; the response says `appliesAt: "next_turn"`.
5. **Session token cap, enforced before each turn, fail closed.** Before the model call, `tokens_in + tokens_out + tokens_cache_write >= token_limit` returns 409 `SESSION_TOKEN_LIMIT` with `{used, limit}` and emits the budget event. **Mid-turn:** the Claude path reuses the existing per-turn interrupt (`engine.mjs:238-255` budget, `:1832-1856` where `processed > tokenBudget` calls `q.interrupt()`); the route cap's *remaining* amount is passed in as an additional ceiling `min(turnTokenBudget, remaining)`, so a turn that crosses the cap stops cleanly with a result and a resumable transcript, exactly like today's turn budget (user says "continue" after raising the cap). The provider adapter (`runToolTurn`, step cap 12, 8192 output tokens, `providers/adapter/index.mjs:20,144`) checks between steps. **Overshoot is bounded by one model call**, stated in the UI as "limit is approximate to one reply". `0` or null = no cap.
6. **Cheap switch = handoff note plus the last 4 to 6 turns**, built by the same function as 3.4 (T5.1/T5.2): one builder, two uses (ended chat and provider switch). Default note size cap 4000 chars (a **starting value, to be set by bench**, 14.8). The new side never receives the old transcript.
7. **Budget events on the wire (additive, API bump):** SSE `notice` kinds `route_switch` `{from, to, reason}`, `session_budget` `{used, limit, remaining, level: 'warn80'|'reached'}`; the Mac already decodes unknown notices as ignorable (P2 rule, section 4, **confirm in P2**). Phone sees them only through the Mac.

### 14.4 Races and crash cases (each gets a test)

- **Switch during a turn:** stored pending (14.3.4); the in-flight turn finishes on its model. Test: PUT mid-stream, assert the stream's provider unchanged and the next turn uses the new one.
- **Cap reached mid-turn:** interrupt, result event, counters committed once in a `finally` that runs on every exit path (the engine binds the mapping on every exit path, `agent-v2.mjs:549`; same rule). Test: cap below one turn's cost, assert stop, assert counters equal ledger delta, assert next turn refused 409.
- **Two windows on one chat:** the turn lock already serialises v2 turns per (user, chat) (`TURN_IN_PROGRESS`, `agent-v2.mjs:144-214`). PUTs use `switch_seq` compare-and-set: a stale `ifSeq` gets 409 `ROUTE_CONFLICT` with the current row. Test: two PUTs, one wins.
- **Crash between model reply and counter commit:** the counter can **under-count by one turn**, never over-count. Mitigation: write `tokens` from the final `usage` before the terminal event is sent; the existing `recordUsage` happens at the same point. Documented as a bound, not hidden.
- **Server restart:** the row survives (main DB); `warm_json` is trusted (a stale warm only causes one avoidable cold prefill), the in-memory cooldowns are lost by design (`provider-fallback.mjs:44-47`).
- **Quit (live-then-archive 3.2):** `purgeWorkingState` (`kb/chat-lifecycle.mjs:92-112`) gains `deleteChatRoute` inside its transaction: the row's cache and stickiness are meaningless after quit. Delete everywhere (3.5 tombstone replay) and `deleteUserCascade` do the same; `agent_route_events` goes with `AGENT_USER_TABLES`. Idempotent like the rest.
- **Chat deleted while a PUT is in flight:** PUT on a chat with no `agent_sessions` row and no Mac-file-backed `chatSessionId` known to the Mac is the Mac's responsibility; the server creates a row lazily only from a turn or a PUT carrying a valid user, and the purge replay removes strays (the 7-day orphan rule, live-then-archive 3.2, covers a lost tombstone).

### 14.5 Single-copy rule for the handoff note

The **Mac session file owns the note** (`ChatSession.summary` / `summaryUpTo`, 3.4 step 1, derived data, rebuildable). The Mac sends it with the first turn after a switch in `history` (the continuation builder, T5.2); the server does not need to keep the text. So for Mac chats `handoff_note` is **null** and the row keeps only `handoff_up_to` (a pointer, to detect "the note is stale, rebuild"). The **only** case where the server holds the text is a chat with no Mac file yet (the extension side panel, Q-T3 (a), `agentContext.surface: 'extension'`, section 13); that working copy is deleted at archive, and the archive protocol writes it into the Mac file's `summary` (one copy again). **At quit the route row, including any server-held note, is purged**; the Mac file keeps summary, chosen provider/model and limit as chat settings (optional keys, mirrored in `chat-tags.json` for N-1, F14 of live-then-archive). On the next open the Mac PUTs the settings back, which recreates the row. **Open consequence (Q-R2):** tokens used are mirrored to the file (`routeTokensUsed`, optional) on archive and re-seeded by that PUT, so the cap survives a quit; a client can lower its own number, which only defeats the user's own limit.

### 14.6 Optional prompt compression (switch, default off, bench-gated)

A stage `providers/compress.mjs`, applied to **provider-adapter turns only** (never the Claude SDK path, whose prompt we do not build: the SDK owns the transcript) and to the handoff builder: (a) dedupe repeated tool outputs and identical file reads, (b) tool-output filtering (cap by chars, keep head and tail, same shape as `TOOL_EVENTS_PER_RUN` style caps), (c) stale-context trimming (drop tool results older than N turns, replaced by a one-line stub). **JSON compaction is out of scope for v1** (changes bytes a model may quote). Kill switch `LLMIDE_ROUTER_COMPRESS=off|on` (default `off`). Redaction runs first (`redaction`, already used by the engine). No compression result is stored.

### 14.7 Learned per-key limits (fills the Phase 6 gap)

`getLimits` knows only built-in provider ids (`kb/usage.mjs:230`, `want = PROVIDERS`), so catalog connections have no limits (provider-catalog spec section 8, last paragraph). Add `provider_learned_limits` (main DB, same migration `0053`, `user_id`-keyed): `(user_id, provider, model, rpm, rpd, tpm, tpd, source ('header'|'429'|'user'), observed_at)`. Fed from `recordRateLimits` header snapshots (`kb/usage.mjs:660`) and from 429 bodies; read by `pickTurnProvider` in addition to the quota and cooldown checks (`provider-fallback.mjs:103-104`) as `limit_near` (at 90% of a learned RPM/TPM within the window) with a per-key cooldown and **next-model retry on the next turn only** (never mid-stream, 14.3.4). A user value (`source: 'user'`) always wins. Learned values expire after 24 h without a fresh observation. The "stacking free tiers" caution (R16) applies unchanged: ordered list only, no rotation across accounts. Kill switch `LLMIDE_ROUTER_LEARN=off`.

### 14.12 Risks and could-not-verify

- **R-R1** A wrong TTL makes the router switch early (one avoidable cold prefill) or stay sticky too long (a rate-limited provider kept one turn longer). Bounded; mitigated by TTLs only gating *optional* switches.
- **R-R2** Handoff note loses detail; the new model answers confidently from a thin summary. Same risk as 3.4; mitigated by `search-kb` on-demand and the last 4 to 6 turns verbatim.
- **R-R3** Counters under-count by one turn after a crash; the cap is "approximate to one reply" and the global ledger budgets are untouched.
- **R-R4** Sticky pinning by a client could hide a cheaper model; the UI shows the pin and who set it (`pinned_by`).
- **R-R5** Secrets in a handoff note: redaction first, size cap, never logged, never in `agent_route_events`.
- **R-R6** More switches means more provider terms surface (free tiers): the ordered-list rule stands (R16).
- **Could not verify:** FreeLLMAPI and OpenRouter behaviour (the user's sources, not opened here); any non-Anthropic cache TTL; the Anthropic 1 h subscription TTL; whether `engine.mjs`'s interrupt path leaves usage totals complete when the cap trips (T6b.3 test); the agent run table has **no chat session column** (`0001_agent_store.sql:25-47`), so per-chat totals cannot be reconstructed from `agent_runs`, which is why the counters are kept on the route row; Mac `ChatSession` and header code not read; no test or bench run.
