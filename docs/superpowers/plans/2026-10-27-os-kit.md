# Plan: os-kit — the Agentic OS view (kit 1)

**Date:** 2026-10-27
**Status:** Approved 2026-10-27 — System view on Home (Mac), no extension tab, React in a web view
**Parent:** [kit-by-kit migration](2026-10-27-kit-by-kit-migration.md) (os-kit section)

## What the user sees

The Mac app's **Home** page becomes the **System** view when a project is open
(today Home opens the user's chosen landing page, default Explorer). No new
top-menu item. With no project open, Home still shows the Welcome screen; the
existing *Settings → Workspace → Home section* picker still lets a user choose
another landing page. The Chrome extension gets nothing for now.

```
┌ System map ───────────────────┬ Running now ─────────────────┐
│ kits on/off + health,         │ chat turn  Sonnet 5.5  [stop] │
│ delegated vs project-owned    │ meeting agent  …       [stop] │
├ Activity timeline ────────────┴───────────────────────────────┤
│ 13:02 chat turn 26.6k tok · 12:58 Box ingest 14 notes · …      │
├ Token flow ───────────────────┬ Memory & knowledge ───────────┤
│ by surface/model, cache       │ project facts, sources, code   │
│ read vs write, prefix vs      │ graph freshness, pending       │
│ transcript                    │ reviews                        │
└───────────────────────────────┴───────────────────────────────┘
```

Read-only, **no model calls**: every number comes from data the server
already records.

## Where the data comes from (K0 map, 2026-10-27)

| Panel | Source today |
|---|---|
| System map | `config.features` + `/health` checks; kit list is static (the kit table) |
| Running now | v2 chat turns (`inFlightAborts`, cancel = `POST /agent/v2/cancel`), meeting-agent runs (`listRuns`, cancel = `POST /kb/agent/stop`), live capture sessions |
| Activity | `activity` table (11 kinds, last 500 per user), `chat_sessions` |

Gaps (the server cannot see these yet): Loop journal, Auto Task schedules and
history, Mac chat transcripts, Library notes on disk. **v1 shows server data
only** and labels Loop/Auto Task as "on this Mac — coming in automation-kit";
the job runner in that kit moves the state server-side, at which point it
appears here with no view change.

## Decision (confirmed 2026-10-27)

**OS-3 technology: React in a WKWebView.** **React in a WKWebView**, built once and
reused by the future desktop app (code reuse, one look via ui-kit tokens).
Cost: a Vite build step joins the Mac build and the panel is a web view.
Rejected alternative: native SwiftUI now (simpler Mac build, best Mac feel) and a
second React version for the desktop app later (two implementations).

## Revision 2 (2026-10-27): the visual Agentic OS, in the Graph section

The user reviewed the first System page (a card dashboard) and wants a far more
visual view, in the spirit of the "Rubric Agentic OS": a living graph "brain" in
the centre, a ring of recent work orbiting it, and panels around the edge.

**Placement (user decision).** Home opens the **Graph** section. The Graph
section's default page is the visual System view; a toggle switches to the
existing code graph. **Explorer** becomes an ordinary top-menu item. (A build
without `code_graph_3d` falls back to Explorer as Home — `resolveHome` already
does this.)

**Ownership (user decision).** The graph is graph-kit's domain, so the reusable
parts move into graph-kit's TypeScript side (a new `web` entry), shared by the
Mac web view now and the desktop (Tauri) app later:

| Part | Where |
|---|---|
| System graph builder: system state (kits, skills, sessions, activity, memory) + the project's code/knowledge graph → one canonical graph-kit graph | graph-kit `typescript/src/system/` |
| Orbit layout: dense 3D core (the code/knowledge graph, force/sphere) + a ring of recent items ordered by time | graph-kit `typescript/src/layout/orbit.ts` (Swift parity later, if the native view needs it) |
| WebGL renderer: point-cloud core coloured by node kind, slow rotation, ring nodes with labels, hover/click events | graph-kit `typescript/src/web/` (three.js) |
| Page, panels and bridge | LLM-IDE `ui/os-view/` (panels from OS-1 data) |
| Section switch, Home, Explorer menu item, graph data via the native bridge | LLM-IDE Mac (`Core/Contracts` seam so Code Graph embeds the System view without naming the System feature) |

**Centre "brain" (chosen by Claude, user deferred).** The open project's real
code + knowledge graph as a point cloud (nodes coloured by kind: code, docs,
tests, knowledge sources), capped for speed (largest communities kept, never
edges pruned — weighted, per the graph-kit rule). Orbit ring = recent activity
(chat turns, ingests, Loop/Auto Task runs, dispatches), clickable.

**Panels.** Left: System map (kits/health), Running now, Skills deck
(`/kb/agent/skill-library`). Right: Token flow, Memory & knowledge, Routines
(Auto Task schedule, supplied natively — Mac-only data).

**Steps.** G1 graph-kit web module (builder + orbit layout + renderer, tests,
demo page) → G2 Mac: section/Home/Explorer menu + graph data and routines over
the bridge → G3 os-view redesign around the renderer → G4 review (Sonnet per
step, Fable for the kit) → graph-kit push + version pin, then LLM-IDE push.

## Revision 3 (2026-10-27): the whole OS view lives in graph-kit

**User decision.** Everything OS-related moves into graph-kit except the bridge.
graph-kit owns the system graph builder, the orbit layout, the WebGL renderer,
**and the whole page**: controller, panels, styles. LLM-IDE keeps only a *host*
that implements graph-kit's `OsHost` interface over the native bridge (Mac) or
plain HTTP (dev). The Mac section and menu wiring also stay in LLM-IDE. Code is
written by Haiku 5.5 and reviewed by Sonnet 5.5.

**Boundary: `OsHost` (graph-kit `web/src/host.ts`).** graph-kit never knows an
LLM-IDE URL, token or message name. The page asks its host for data:

```ts
interface OsHost {
  loadState(range: 'day' | 'week'): Promise<OsSnapshot>; // rejects OsAuthError on 401
  cancel(request: OsCancel): Promise<void>;
  watch(onChange: () => void, onStatus: (s: OsLiveStatus, detail?: string) => void): () => void;
  open(target: string): boolean;                          // false = nowhere to go
  loadProjectGraph?(): Promise<CGData | null>;            // the brain; null = none yet
  loadSkills?(): Promise<OsSkill[]>;                      // Skills deck
  loadRoutines?(): Promise<OsRoutine[]>;                  // Routines (Mac-only data)
}
mountOsView(root: HTMLElement, host: OsHost, opts?: { theme?: string; projectName?: string | null }): OsViewHandle
// OsViewHandle: configure({ theme?, projectName? }), notifyChange(), dispose()
```

`OsSnapshot` is graph-kit's own structural type for `/kb/os/state`. LLM-IDE pins
`GetKbOsStateResponse200` as assignable to it with a `tsc` check, so a contract
drift still fails the build.

**Layout in graph-kit.**

| Path | What | Deps |
|---|---|---|
| `typescript/src/system/` | `OsSnapshot` types, `buildSystemGraph(snapshot, projectGraph, opts)` → core (capped by community) + ring (recent activity, by time), `orbitLayout(systemGraph, opts)` deterministic 3D positions | none (pure, node --test) |
| `web/` (new package `@dnsmalla/graph-kit-web`) | `OsHost`, `OsController` (host-based, timers injected), `mountOsView`, panels (React), styles, `OrbitView` three.js renderer, demo page on a fixture host | react, react-dom, three (peer + dev) |

The Node package (`typescript/`) stays dependency-light: the WIP commit that
added `three` to it is reverted.

**LLM-IDE side.** `ui/os-view` keeps `bridge.ts`, `api.ts`, `sse.ts`,
`stream.ts` and the dev connect form, implements `OsHost` twice (native, dev)
and imports graph-kit's page from the submodule source through a Vite alias
with `resolve.dedupe` for react, react-dom and three. The bundle is still
committed and `make os-view-check` still gates it. Any CI job that runs it
checks out the graph-kit submodule only (the `graph-gates` precedent).

**Steps (graph-kit branch `feat/system-orbit`, LLM-IDE branch `feat/kit-ui`).**
1. K1 `typescript/src/system/`: types + `buildSystemGraph` + tests.
2. K2 `typescript/src/system/orbit.ts`: orbit layout + tests.
3. K3 `web/` scaffold: `OsHost`, controller ported from `ui/os-view/src/controller.ts` onto the host, current panels and styles moved, ported tests.
4. K4 `OrbitView`: the three.js renderer + demo page.
5. K5 page redesign: brain in the centre, left = System map / Running now / Skills deck, right = Token flow / Memory & knowledge / Routines.
6. L1 `ui/os-view` becomes the host + mount. Rebuild the bundle, run the tests and `os-view-check`.
7. G2 (next): Mac side. Project graph, skills and routines over the bridge; Home → Graph section with the System | Code graph toggle; Explorer becomes a top-menu item.

### Revision 3a (2026-10-27): the OS graph core is Rust

**User decision.** The graph part moves to Rust. The scope chosen is the **OS
graph core only**: the system graph builder and the orbit layout. They become
the graph-kit crate `rust/os-graph` (`graph-kit-os`, serde only, an optional
`wasm` feature with JSON-in/JSON-out `wasm-bindgen` entry points). It is the
canonical implementation.

`typescript/src/system/` stays only as the parity oracle.
`typescript/scripts/gen-os-golden.mjs` writes golden cases that
`rust/os-graph/tests/parity.rs` asserts: graphs exact, coordinates within 1e-9.

The React page and the three.js renderer stay TypeScript. Once the WASM build
exists, `web/` calls the crate and the TS copy is deleted. The build needs
`rustup` + `wasm32-unknown-unknown` + `wasm-bindgen-cli`, none of which are
installed on the dev Mac yet.

### Revision 4 (2026-10-27): the whole OS as a graph, with drill-down

**User feedback on the first real run.** The brain rendered real data, but
nothing on the page was interactive: no zoom, no way to see code or file
structure, and the agent panels were display-only.

**User decision.** Everything in the OS is a graph. Clicking any part opens that
part's own graph.

The scene has two levels. **Level 1 is the OS graph.** Each labelled hub is
listed below with the members clustered around it:

| Hub | Members |
|---|---|
| Code | code clusters |
| Knowledge | source kinds |
| Memory | repos and their fact counts |
| Skills | skills, grouped by source |
| Models | models sized by tokens, linked to sources (api, cli, auto-task) and endpoints |
| Agents | running chat turns and meeting-agent runs |
| Routines | Auto Tasks |
| Kits | kits linked to the features they need |

Recent activity orbits the scene. **Level 2 is a hub's own graph.** Clicking a
hub opens it, with a breadcrumb back. Code is the full code brain. Clicking a
node inside a level-2 graph shows its details: file, neighbours, code preview,
open in Explorer.

The graph builders are Rust (`rust/os-graph`). One generic `VizGraph` (typed
nodes with kind, group, size, label and drill target, plus edges) feeds one
layout (orbit, with community = group) and one renderer (`OrbitView`). Hubs
get visible labels.

**Steps.**
- K6a: interaction — orbit, zoom, pan, pinch, focus, highlight, cluster
  colours, search.
- R1: Rust `VizGraph` builders for the OS level and each hub, with WASM
  exports.
- K7: the web renders `VizGraph` at both levels, with drill-down, breadcrumb
  and labels.
- K6b: node details, code preview, file tree, clickable panels.
- G3: the Mac bridge can open a file and read a file.
- L2: the host wires `openFile` and `loadFile`, and the bundle is rebuilt.
