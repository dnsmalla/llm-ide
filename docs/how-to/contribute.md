# How to contribute

> Conventions for committing code to LLM-IDE.

## Goal

Land a change that's reviewable, doesn't regress invariants, and keeps the docs in sync.

## Steps

### 1. Before you start

- For non-trivial changes, scan [Engineering invariants](../explanation/invariants.md) — especially the section for the file you're about to edit.
- For a new architectural direction, write an ADR first (`docs/decisions/NNNN-<title>.md`, status `proposed`). Get it reviewed before code.

### 2. Code style

- TypeScript: strict mode, no `any`, no widening.
- Server: pure Node `http`, ESM (`.mjs`), no new framework.
- No new dependencies without justification in the PR description.
- One logical change per PR.

### 3. Security ground rules (non-negotiable)

- No wildcard CORS. ([ADR 0005](../decisions/0005-strict-cors-allowlist.md))
- No API key inputs; LLM calls go through `claude -p`. ([ADR 0001](../decisions/0001-claude-cli-not-api-key.md))
- No new vault key without updating the allowlist in `extension/server/vault.mjs`.
- User content is always wrapped in `<<<BEGIN>>>…<<<END>>>` fences and sanitised first.
- No new dispatch path that bypasses the review queue.
- Bump `SERVER_API_VERSION` when changing the wire format; update `REQUIRED_ENDPOINTS` in `App.tsx`.

### 4. Docs accompany code

If you add an endpoint → update [`docs/reference/api/overview.md`](../reference/api/overview.md) and `docs/reference/api/openapi.yaml`. If you change an invariant → update [invariants.md](../explanation/invariants.md). If you make an architectural decision → add an ADR.

### 5. Generated files

- **`schema/http/INVENTORY.md` is a generated snapshot.** Never hand-edit it and never commit it just to make a push pass. The contract gate validates route coverage from the generator output (`node scripts/http-inventory.mjs --coverage`), not the committed diff, so a stale copy does not fail a push.
- Run `make inventory` only when you want a current copy in the working tree (e.g. to read the caller table); CI regenerates the file and uploads it as the `http-inventory` artifact. `make inventory-check` is the full drift check, for a deliberate audit.
- Do not add a "regenerate the inventory" commit to a feature PR. If a route change leaves it stale, that is expected.

### 6. Commits

- Conventional-commit style: `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`.
- One logical change per commit when feasible; one logical change per PR always.
- Stage explicit paths (`git add <paths>`), never `git add -A`.

### 7. Releasing

1. Bump `extension/package.json` version.
2. Bump `SERVER_API_VERSION` if endpoints changed.
3. Update README badges if major.
4. Tag `vX.Y.Z`.
5. Tag `desktop-vX.Y.Z` if shipping a paired desktop release ([desktop-release.md](desktop-release.md)).

## Verification

```bash
cd extension
npm run type-check
npm test
```

Both must pass before opening a PR. For anything that touches `schema/`, `scripts/`, `extension/`, `ui/`, `desktop/`, `web/`, `Makefile` or `docs/reference/api/`, also run the push gate:

```bash
make contract-gates   # coverage from the generator output, fixtures, generated types/OpenAPI/tokens
make regression       # full pre-push gate (contract-gates + desktop/ui/web + agent/v2 + graph-kit)
```

`make hooks` installs the scoped pre-push hook, which runs the same gates for what changed. It prints a note when `schema/http/INVENTORY.md` is stale and still pushes: the snapshot is regenerated by CI, never by a hand commit. Never use `--no-verify` to work around a real coverage failure; fix the route/roster or add a reasoned allowlist entry.
