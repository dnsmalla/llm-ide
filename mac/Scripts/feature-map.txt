# path-prefix   layer            sealed?
# First matching prefix wins, so list most-specific prefixes first.
# Layer is: Core | Shell | Feature:<Name>
# A third column of `sealed` means the feature is enforced at ZERO
# cross-feature references. Unsealed features are reported only.
# Unlisted paths default to Unclassified, a real (non-exempt-from-reporting)
# layer: a classified Feature referencing Unclassified code produces a
# non-failing `pending` line instead of vanishing silently. Shell/Core stay
# exempt from the cross-feature BOUNDARY rule (they may reference anything)
# but are NOT exempt from the build-exclusion rule (see feature-boundaries.sh).
# Seal a feature only once its collaborators are classified too — sealing
# early hides real edges to still-unclassified code (Gantt was once sealed
# while Issues was still unclassified, so its seal passed only because its
# edges into Issues were invisible — commit 09693696).
# Menu items that one LLMIDE_FEATURES key excludes together AND that reference
# each other are one unit, so they share one folder and one row here: their
# menu items are sub-folders this prefix owns (Features/Generation/{DocGen,
# Visual}/, Features/Issues/Gantt/). As separate rows the unit's internal
# edges were reported as cross-feature — a cycle no seal could ever pass.
