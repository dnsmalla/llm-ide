## 1. Strong Formulation

### Definition
For two formulations A, B of the same problem, let P_A and P_B be their LP relaxation feasible regions. If **P_A ⊂ P_B**, then A is "stronger" (LP relaxation is closer to the integer hull).

### Significance of Strong Formulation
- LP relaxation value close to integer optimal ⇒ Branch-and-bound pruning efficiency increases dramatically.
- It is not uncommon for root LP gap to shrink from 10% → 1% and solve time to decrease by orders of magnitude.

### Representative Example: Facility Location
| Constraint | LP Relaxation Strength |
|---|---|
| `Σᵢ xᵢⱼ ≤ M·yⱼ` (aggregated) | Weak. M=\|I\| gives root gap of tens of percent |
| `xᵢⱼ ≤ yⱼ ∀i,j` (disaggregated) | Strong. In UFL, LP-optimal = integer-optimal is common |

### Constraint Addition Cost
- Aggregated version: O(\|J\|) constraints
- Disaggregated version: O(\|I\|·\|J\|) constraints
- Even with more constraints, presolve often reduces them, limiting LP solve time increase.

### Representative Valid Inequalities / Cuts
- **Cover Inequality** (for knapsack structure): C ⊆ N, Σ_{j∈C} w_j > W implies Σ_{j∈C} x_j ≤ \|C\| − 1
- **Flow Cover** (for fixed-charge flow)
- **Clique Inequality** (for conflict graph among binary variables): for clique K, Σ_{j∈K} x_j ≤ 1
- **Chvátal-Gomory cut**: integer rounding
- **MIR (Mixed Integer Rounding)** cut
- **GMI (Gomory Mixed Integer)** cut
- **Lift-and-Project** (Balas-Ceria-Cornuéjols 1993)
- Most are auto-generated by commercial solvers. Manual addition is useful when exploiting problem-specific structure (e.g., RCI for VRP, comb inequalities for TSP).

## 2. Big-M Design

### Basic Guidelines (Gurobi Official)
> "Setting M equal to the largest of the absolute values of the lower and upper bounds of x and y (if they are present) often works well."

**Make M as tight as possible to the theoretical upper bound.**

### Common Bad Examples
```python
# NG: Always 1e6
model.addConstr(s_j >= s_i + p_i - 1e6 * (1 - z))
```
LP relaxation becomes nearly unconstrained → branching explosion + "trickle flow" numerical errors (values that should be 0 persist as ~1e-9).

### Good Design
```python
# JSP disjunctive constraint (order of i vs j on machine k)
# s_jk + p_jk ≤ s_ik + M·z_ijk  (if z=0, j comes first)
# M can be set to the makespan upper bound
M = sum(p[i, k] for i in jobs for k in machines)  # theoretical upper bound
# Even tighter: M = ub(s_ik) - lb(s_jk + p_jk)
```

### Tighten Variable Bounds Before Deriving M
- For time variables, precompute feasible time ranges with CP (`feasible_start_times`).
- For flow variables, derive bounds from capacity constraints.
- Gurobi/CPLEX presolve automatically tightens bounds, but providing initial bounds makes it even more effective.

### "Trickle Flow" Phenomenon
When Big-M is too large + flow variables that should be zero in the optimal solution have tiny values (e.g., 1e-8). While this does not affect integer solutions, it indirectly causes longer solve times and downstream numerical issues.

## 3. Converting Logic Constraints to MIP

### 3.1 "x ≥ d ⇔ b = 1" (Triggered by Binary b)
```
x ≥ d − M(1 − b)        (if b=1, enforces x ≥ d)
x ≤ d − ε + Mb           (if b=0, enforces x < d, ε is tolerance)
```
- ε is numerical precision (e.g., 1e-5). Setting to 0 makes b ambiguous at equality.

### 3.2 "a^T x ≤ d ⇒ b = 1" (One-directional)
```
a^T x − d ≤ M·b
```

### 3.3 "if x > y then b = 1"
```
x − y ≤ M·b
x − y ≥ ε − M(1 − b)
```

### 3.4 Disjunction "A or B"
At least one of two linear constraint systems must be satisfied:
```
A: a^T x ≤ b
B: c^T x ≤ d
z ∈ {0, 1}
A: a^T x ≤ b + M(1 − z)
B: c^T x ≤ d + Mz
```

### 3.5 AND / OR / NOT
For binary variables b1, b2:
- AND: `b₁ + b₂ ≤ 1 + y, y ≤ b₁, y ≤ b₂` (y = b1 ∧ b2)
- OR: `b₁ + b₂ ≥ y, y ≥ b₁, y ≥ b₂` (y = b1 ∨ b2)
- NOT: `y = 1 - b₁`
- XOR: `b₁ + b₂ = 1`

### 3.6 If-then-else
"If b=1 minimize f(x), else minimize g(x)":
```
z = f(x)·b + g(x)·(1−b)  → hard to linearize. Instead:
z ≥ f(x) − M(1 − b)
z ≥ g(x) − Mb
```

### Textbook
H. P. Williams, *Model Building in Mathematical Programming*, 5th ed., Wiley 2013 is standard.

## 4. Piecewise Linear Functions (PWL)

For convex PWL, use epigraph with only linear constraints. For nonconvex, discrete choice is necessary.

### 4.1 Convex PWL (No Binary Needed)
```
f is convex, breakpoints a_1 < a_2 < ... < a_K
We want to minimize f(x)
```
For each segment (slope m_k, intercept b_k):
```
y ≥ m_k · x + b_k    ∀k
min y
```

### 4.2 Nonconvex PWL (Binary Needed)
Lin (2013) "A Review of Piecewise Linearization Methods," *Math. Problems in Engineering* provides a review. Vielma, Ahmed, Nemhauser, *OR* 58(2):303-315, 2010 compares formulation strength.

#### CC (Convex Combination)
```
x = Σ_k a_k · λ_k
y = Σ_k f(a_k) · λ_k
Σ_k λ_k = 1, λ_k ≥ 0
Only two adjacent non-zero → enforced via SOS2
```

#### Incremental (Markowitz-Manne)
The first j-1 segments are fully used, segment j is partially used:
```
x = a_1 + Σ_{k=1}^{K-1} (a_{k+1} − a_k) · δ_k
y = f(a_1) + Σ_{k=1}^{K-1} (f(a_{k+1}) − f(a_k)) · δ_k
δ_k ∈ [0, 1]
δ_k ≤ z_k   (z_k ∈ {0,1})
δ_{k+1} ≤ z_k
```
**Locally ideal (Padberg)**: LP relaxation is the integer hull itself. Good performance.

#### Logarithmic (Vielma-Nemhauser 2011)
Represent K segments with log₂(K) binaries. **Tight LP relaxation**. Clever construction like gray code.

#### SOS2
Without binaries, "only two adjacent non-zero" is enforced via branching. Beale-Tomlin 1970. Gurobi's `addSOS(GRB.SOS_TYPE2, vars)` can be used.

### 4.3 Implementation Recommendations
- **For convex minimization, use epigraph**, no binaries needed.
- **For nonconvex, use Incremental or Logarithmic** as first choice. CC + SOS2 is also good but branching can be slow.
- Gurobi 9+ `addGenConstrPWL` automatically selects appropriate formulation internally. More stable than writing by hand.
- **Gurobi 12 (Dec 2024)** introduced exact nonlinear constraints via `addGenConstrNL`, superseding the older piecewise-approximation function-constraint API. Confirm against your installed version's docs.

## 5. Symmetry Breaking

### 5.1 Harm of Symmetry
Symmetric sub-problems expand K! times → branch-and-bound tree becomes exponentially redundant.

### 5.2 Representative Problems with Symmetry
- Parallel identical machine scheduling (m identical machines)
- Bin packing (bin permutation equivalence)
- Graph coloring (color permutation equivalence)
- Statistical experimental design (block permutation)
- Network design (node/edge label permutation)
- See Margot, "Symmetry in integer linear programming," in *50 Years of Integer Programming 1958-2008*, Springer 2010, DOI 10.1007/978-3-540-68279-0_17 for a review.

### 5.3 Static Symmetry Breaking (Added as Constraints)
#### Lex Order
```
y_1 ≥ y_2 ≥ ... ≥ y_K    (bin packing: sort by bin index)
```
#### Fix First Element
```
x_11 = 1                  (item 1 always goes to bin 1)
```
#### Anti-lex (Cumulative)
```
Σⱼ≤k y_j ≥ Σⱼ≤k+1 y_j     (used bins are consecutive indices)
```

### 5.4 Dynamic Symmetry Breaking
- **Orbital branching** (Ostrowski et al., *Math. Prog.* 126(1):147-178, 2011)
- **Orbitopal fixing** (Kaibel-Peinhardt-Pfetsch, *Math. Prog.* 126(1):29-65, 2011)
- **Isomorphism pruning** (Margot, *Math. Prog.* 94(1):71-90, 2002 and sequels)
- Gurobi/CPLEX apply some of these automatically via `Symmetry` parameter (enabled by default).

### 5.5 Implementation Priority
1. First try lex order or fix-first (simple, one line to add).
2. Enable solver's auto symmetry detection.
3. If still slow, implement orbital branching with pyscipopt, etc.

### 5.6 Cautions
- Static breaking makes "only the lex-minimal symmetric solution feasible." LP relaxation may simultaneously become tighter.
- However, inappropriate breaking can exclude optimal solutions. **Always verify correctness after implementation** (check small instances against brute force).
- Watch for conflicts with business constraints (e.g., "machine 1 is new so prioritize its use").

## 6. Linearization Techniques

### 6.1 Binary × Binary
z = x · y (x, y ∈ {0,1}):
```
z ≤ x
z ≤ y
z ≥ x + y − 1
z ∈ {0, 1}  (or continuous in [0,1])
```

### 6.2 Binary × Continuous
z = x · y (y ∈ {0,1}, 0 ≤ x ≤ U):
```
z ≤ U · y
z ≤ x
z ≥ x − U(1 − y)
z ≥ 0
```

### 6.3 Absolute Value (When Minimizing)
```
min |x| → min z s.t. z ≥ x, z ≥ −x
```
Does not work for maximization or equality constraints (only one direction is correct).

### 6.4 max / min (When Minimizing)
```
min max(x, y) → min z s.t. z ≥ x, z ≥ y
```

### 6.5 Ratio (Fractional Objective)
```
max (cᵀx + α) / (dᵀx + β)
```
**Charnes-Cooper transformation**: Let y = x/t, t = 1/(dᵀx+β), then:
```
max cᵀy + αt
s.t. dᵀy + βt = 1
     Ay − bt ≤ 0
     y, t ≥ 0
```
Reduces to LP (for continuous variables). For integer variables, becomes mixed-integer linear fractional programming, requiring different methods (Dinkelbach 1967, parametric).

### 6.6 Bilinear (McCormick Envelopes)
z = x · y, x ∈ [xᴸ, xᵁ], y ∈ [yᴸ, yᵁ]:
```
z ≥ xᴸ·y + x·yᴸ − xᴸ·yᴸ
z ≥ xᵁ·y + x·yᵁ − xᵁ·yᵁ
z ≤ xᴸ·y + x·yᵁ − xᴸ·yᵁ
z ≤ xᵁ·y + x·yᴸ − xᵁ·yᴸ
```
- Use spatial branch-and-bound to improve accuracy (BARON, Couenne, Gurobi 11+ with `NonConvex=2`).

## 7. Reformulation

### 7.1 Variable Aggregation → Disaggregation
A typical cure for weak formulations.

### 7.2 Position Variables → Flow Variables
- VRP's MTZ order variables → multi-commodity flow. LP relaxation may become stronger in some cases.
- Trade-off: variable count explodes.

### 7.3 Time Variables → Time-Indexed
- Continuous time + Big-M disjunction → discrete time + xᵢⱼₜ.
- Effective if time grid T is small, explodes if large.

### 7.4 Set-Partitioning Reformulation
- Standard pattern for VRPTW, crew scheduling, bin packing, cutting stock.
- Columns are exponential ⇒ use column generation.

### 7.5 Lagrangian Dual Reformulation
- Incorporate complicating constraints as penalty in objective.
- If remaining subproblem is decomposable, achieves speedup.
- Held-Karp's TSP 1-tree relaxation is a classical example.

## 8. Indicator Constraints vs Big-M

### 8.1 Indicator Constraints
```
y = 1 ⇒ a^T x ≤ b
```
Gurobi: `model.addGenConstrIndicator(y, True, lhs, GRB.LESS_EQUAL, b)`
CPLEX: `IndicatorVar`
- Internally often converted to Big-M via SOS1.
- Controlled by Gurobi's `PreSOS1BigM` parameter.

### 8.2 Trade-offs
| Aspect | Indicator | Big-M |
|---|---|---|
| Numerical Stability | Good (independent of M) | Deteriorates with large M |
| Computation Speed | Usually slightly slower | Fast with tight M |
| LP Relaxation | Somewhat weak | Strong if M is tight |
| Implementation | One API line | Compute M yourself |

### 8.3 When to Use Which
- **Tight Big-M is easy to compute** ⇒ Big-M recommended
- **M is large or unclear, numerical stability paramount** ⇒ Indicator recommended
- **Hybrid**: Some constraints Big-M, some Indicator, is OK.

Gurobi Help Center post: "Why is using Indicator Constraints in Gurobi significantly slower than the Big-M method" — Big-M is faster at scale, but wrong M gives wrong solution.

## 9. SOS1 / SOS2 Constraints

### 9.1 SOS1 (Special Ordered Set 1)
"At most 1 variable is non-zero in the set"
```
SOS1: {x₁, x₂, ..., xₙ}, at most 1 ≠ 0
```
- Can be written with binary + Big-M (zⱼ ∈ {0,1}, Σzⱼ ≤ 1, xⱼ ≤ M·zⱼ), but declaring as SOS1 lets the solver use specialized branching.
- Use cases: discrete choice, fixed-cost activation.

### 9.2 SOS2 (Special Ordered Set 2)
"At most 2 adjacent variables are non-zero in the set"
```
SOS2: {λ₁, λ₂, ..., λₙ}, at most 2 adjacent non-zero
```
- Used in CC formulation of PWL to enforce "only 2 adjacent segments are active."
- No binaries needed; branching enforces the constraint while preserving LP relaxation.

### 9.3 Implementation Example (Gurobi)
```python
import gurobipy as gp
model = gp.Model()
lambda_vars = [model.addVar(lb=0, ub=1) for _ in range(K)]
# Declare as SOS2
model.addSOS(gp.GRB.SOS_TYPE2, lambda_vars)
```

### 9.4 Cautions
- SOS is powerful in modern solvers, but some implementations convert to Big-M internally.
- OR-Tools CP-SAT has no direct SOS support (substitute with CP logical constraints).

## 10. Convex QP Epigraph Form (Keeping Nonconvex Sets Convex in Writing)

### 10.1 Problem
When writing "cost = α·x² + β·x + γ" (α > 0) as a constraint:

#### Nonconvex Writing (NG, Requires NonConvex=2)
```
y == α·x² + β·x + γ         (equality constraint)
```
or
```
y ≤ α·x² + β·x + γ          (upper bound, under parabola = nonconvex)
```
Feasible region is below or on the parabola → **nonconvex set**. Gurobi's default QP solver cannot solve it. Requires `NonConvex=2` and spatial branch-and-bound, which is slow.

#### Convex Writing (Recommended, Solvable by Default)
```
y ≥ α·x² + β·x + γ          (lower bound, above parabola = convex epigraph)
min y
```
- Feasible region is above the parabola = convex set (epigraph)
- Solvable by Gurobi's default QP solver

### 10.2 Applicable Patterns

| Objective | Recommended Form |
|---|---|
| `min α·x²` (α > 0) | As-is (quadratic objective, convex) |
| `min y, y == x²` | Rewrite as `y ≥ x²` (equality → inequality, convex) |
| Modeling `cost(x) = x² + ...` | Write as `y ≥ ...` and `min y` |
| Capacity `Σ Q_j · x_j² ≤ C` (Q_j > 0) | As-is (convex constraint, SOCP) |
| `Σ p_j · x_j² ≥ K` (quadratic lower bound) | Nonconvex, avoid / consider linearization |

### 10.3 Computational Time Experience (Within GRID Projects)
- 4900 rows × 9500 columns scale: quadratic still takes ~1.5x linear time
- 45000 rows × 30000 columns scale: quadratic causes major slowdown, impractical
- Larger scale makes linearization or epigraph form more effective

### 10.4 Reduction to SOCP

Some convex QP can be written as SOCP (Second-Order Cone Program):
```
‖A·x + b‖₂ ≤ cᵀx + d
```
This achieves further speedup (Mosek, Gurobi's SOCP mode).

## 11. Gurobi Auto Big-M vs Manual Linearization

### 11.1 Gurobi's Automatic Big-M
Gurobi automatically applies Big-M linearization even if you naively write binary × continuous product `z = bin · cont`:
```python
# Naive writing
model.addConstr(z == bin_var * cont_var)  # Gurobi auto-applies Big-M
```

### 11.2 Manual Linearization is Often Faster
However, **manual writing is often faster** (demonstrated in GRID Kansai PoC, Hokkaido project, etc.):

```python
U = 100  # upper bound of cont_var (compute tight bound)
model.addConstr(z <= U * bin_var)
model.addConstr(z <= cont_var)
model.addConstr(z >= cont_var - U * (1 - bin_var))
model.addConstr(z >= 0)
```

Reasons:
- Automatic conversion does not fully exploit problem-specific bounds information
- User, understanding model context, can compute **tighter U**
- Automatic conversion applies a generic template, leaving room for tighter formulation

### 11.3 Empirical Example (GRID Kansai PoC)
> "Gurobi, being smart, automatically uses Big-M internally to linearize. However, after we explicitly linearized it by hand, computation time shortened."

### 11.4 Decision Criteria
- Prototype stage: OK to rely on Gurobi's auto Big-M
- Performance tuning stage: Try manual linearization + compute tight U
